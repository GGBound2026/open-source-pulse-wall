Git 必修课

AI 写代码越来越快，改坏的速度也一样快。这节课用大白话讲清 Git 的几个核心概念：让你敢放手让 AI 改，也能在出问题时把代码找回来。

开场

你是不是也这样管理过文件？

改一版，存一个副本。几天之后，连你自己都说不清哪个才是对的。

我的主页
  • 主页.html3月1日
  • 主页_改.html3月3日
  • 主页_最终版.html3月8日
  • 主页_最终版2.html3月9日
  • 主页_最终版_改好了.html3月12日
  • 主页_真的最终版_别动.html3月15日
  • 主页_AI改过_备份.html今天

这样做有三个麻烦

  1. 哪个才是最新的？文件名越起越长，还是分不清。
  2. 每一版到底改了什么？只能把两个文件摆在一起，一行行对比。
  3. 想回到“上周还能用的那版”？不知道是哪一个，说不定早就被覆盖了。
Git 就是来解决这件事的。它在同一个文件夹里，帮你记住每一个版本、每次改了什么，随时能回到任何一版。

开场

AI 写代码越快，你越需要 Git

设想一下：你让 AI “给主页加个暗黑模式”，它 30 秒改了 12 个文件，页面却白屏了。怎么办？

没有 Git
能用的主页 AI 改了 12 个文件 白屏了 “快帮我改回去！” AI 也记不清原来的样子 继续瞎改 越改越乱
有 Git
存档：能用的主页 AI 改了 12 个文件 白屏了 “回到上一个存档” 几秒钟恢复原样
敲命令这件事，可以交给 AI。但什么时候存档、要不要开分支、改坏了该怎么回去，得由你来判断、由你来开口。这节课教的，就是你开口时需要的这些“词”。

01 · 存档

先分清：Git 和 GitHub 不是一个东西

Git 是装在你电脑上的一个软件；GitHub 是一个网站，帮你把 Git 管理的项目放到网上。

Git ≈ 游戏的本地存档

在自己电脑上存档、读档，不联网也能用。

GitHub ≈ 云存档 + 玩家社区

把存档传到网上：换电脑也能拿到，还能和别人一起玩。

同类平台还有

GitLab：很多公司在内部自己搭。Gitee：国内访问更快。用法基本一样。

01 · 存档

两个最基本的词：仓库和提交

记住这两个词，你就能和 AI 讨论 Git 了。

仓库（repository）：被 Git 管起来的文件夹

在文件夹里运行一次 git init，它就变成了仓库。千万别手动删掉 .git，删了存档就全没了。

提交（commit）：一次存档

  1. 3f2e1d0加上暗黑模式最新小林 · 今天 14:32
  2. 9c8d7e6换成蓝色主题小林 · 昨天
  3. e4f5a6b加上自我介绍小林 · 3月2日
  4. a1b2c3d创建主页小林 · 3月1日
编号：自动生成，每个存档独一无二 说明：你写的一句话 谁、何时：Git 自动记录
每个存档都是项目在那一刻的完整快照。想翻看存档列表，就运行 git log。

01 · 存档

存一次档，要经过 3 个地方

为什么不能一步存好？因为你常常同时改了好几个文件，却只想把其中一部分存进这次存档。

← → 逐步演示

① 在工作区改文件：你（或 AI）改了 index.html 和 style.css，顺手还写了个 草稿.txt。此时 Git 只是“发现有改动”，还什么都没存。

对 AI 说“现在有哪些改动还没存档？”

$ git status

② 用 add 挑出要存的：只把 index.html 和 style.css 放进暂存区（快递箱），草稿留在桌上，不会混进这次存档。

对 AI 说“把 index 和 style 加入暂存，草稿别加”

$ git add index.html style.css

③ 用 commit 封存：暂存区里的东西被打包成一个新存档，附上一句说明，放进本地仓库。注意：它现在只在你的电脑里。

对 AI 说“提交一下，说明写‘加上暗黑模式’”

$ git commit -m "加上暗黑模式"

01 · 存档 · 小结

第 1 章小结：6 个命令，其实就是 6 句话

不用背。知道有这些动作，需要的时候直接告诉 AI 就行。

你想做什么可以这样跟 AI 说背后的命令
让这个文件夹开始用 Git“把这个项目初始化成 Git 仓库”git init
看看现在改了哪些文件“现在有哪些改动还没存档？”git status
看看具体改了哪几行“给我看看这次具体改了什么”git diff
挑出要存档的文件“把 index.html 加入暂存”git add
存一个档“提交一下，说明写清楚做了什么”git commit -m "…"
翻看存档记录“列出最近 5 次提交”git log
好的提交说明：“加上暗黑模式切换按钮”、“修复手机上导航栏错位”。一句话说清做了什么。
不好的提交说明：“update”、“改了点东西”、“111”。一个月后谁也看不懂。

02 · 分支

分支：开一个平行世界去试错

主页已经能用了，你想让 AI 大改一版，又怕改崩。不用复制整个文件夹，开一个分支就行。

← → 逐步演示

main 是主线：项目默认的那条线，放着“能用的版本”。每个圆点是一次存档，越往右越新。黑色的 HEAD 标签表示“你现在在这里”。

对 AI 说“我现在在哪个分支上？”

$ git branch

新建分支 = 贴一张新标签：redesign 和 main 指向同一个存档。不复制任何文件，一瞬间就完成，HEAD 也跟着你切到了 redesign。

对 AI 说“新建一个 redesign 分支，在上面改”

$ git switch -c redesign

在分支上放心改：新存档只加在 redesign 上，main 原地不动、随时能用。改砸了就切回 main，一切照旧。

对 AI 说“先切回 main，让我看看原来的样子”

$ git switch main

满意了就合并回来：main 拿到了 redesign 的全部改动。不满意？直接删掉这个分支，main 不受任何影响。

对 AI 说“把 redesign 合并到 main”

$ git switch main $ git merge redesign

02 · 分支

合并时会遇到的 3 种情况

大多数时候 Git 会自动搞定。只有两边改了同一处，才需要你来拍板。

← → 逐步演示
index.html
<<<<<<< main ← 当前分支的写法<h1>欢迎来到我的主页</h1>=======<h1>Hi，我是小林</h1>>>>>>>> redesign ← 要合进来的写法

冲突不是出错，是 Git 在问你：听谁的？

  1. 打开冲突的文件，找到这几行记号
  2. 决定留哪一段，或者把两段合起来
  3. 删掉 <<<<<<<、=======、>>>>>>> 这三行记号
  4. 再 add + commit，合并就完成了

快进（fast-forward）：你开分支之后，main 上没有任何新存档。Git 不用真的“合”，把 main 标签往前挪到最新处就行。

对 AI 说“把 redesign 合并到 main”

$ git merge redesign

自动合并：两边各自有了新存档，但改的是不同地方。Git 会自动把两边的改动合到一起，生成一个新的“合并存档”。

对 AI 说“合并完给我看看最后的结果”

$ git log --graph --oneline

冲突：两边改了同一个文件的同一行，Git 不敢替你做决定，只好停下来问你。

对 AI 说“有冲突先列给我看，别替我决定留哪边”

02 · 分支 · 进阶

worktree：让几个 AI 同时开工，互不打架

一个文件夹同一时间只能“站在”一个分支上。两个 Agent 挤在同一个文件夹里改，就像两个人抢一张书桌，难免互相覆盖。

每个 worktree 是一个独立的文件夹，各自站在不同的分支上，改动互不影响；但它们共用同一套存档，做完之后随时可以合并。

对 AI 说“新开一个 worktree 做这个功能，别动我当前的文件夹”

$ git worktree add ../wt-ui -b feat-ui

03 · 后悔药

改坏了？先回答两个问题

选哪种“后悔药”，只看两件事：这次改动存档（commit）了没有，上传（push）了没有。

全搞砸了也别慌：git reflog 像飞机的黑匣子，记着你最近的每一步操作。哪怕误删了存档，通常也能照着记录找回来。直接对 AI 说：“用 reflog 帮我找回刚才丢的提交”。

03 · 后悔药

reset 和 revert：撕掉一页 vs 补一句更正

两个都能“撤销一次存档”。区别在于：会不会改写已经存在的历史。

git reset · 撕掉最后一页

像把日记最后一页撕掉，看起来从没写过。

只能用在还没 push 的存档上。别人已经下载了 C，你这边撕掉了，两边的历史就对不上了。

git revert · 补一句更正

像在日记里补一句“上一条作废”，原来那页还在。

已经上传的存档，用它最安全。历史只增不减，别人同步时不会出问题。
小心 reset --hard：它会把还没存档的改动也一起清掉。让 AI 执行之前，先让它告诉你会丢掉什么。

04 · 协作

远程仓库：让存档在电脑和 GitHub 之间同步

先记住一个最容易搞错的点：commit 只存在你的电脑里，push 之后，GitHub 上的人才看得到。

← → 逐步演示

clone：第一次参与项目时，把 GitHub 上的整个仓库（连同全部存档）下载到电脑上。只需要做一次。

对 AI 说“把这个仓库 clone 到本地”

$ git clone <仓库地址>

commit：你在本地存了一个新档（橙色）。注意看右边：GitHub 上还没有它。commit 不会自动上传。

对 AI 说“提交一下，先别推”

$ git commit -m "加上暗黑模式"

push：把本地的新存档上传到 GitHub。从这一刻起，别人才能看到你的改动。

对 AI 说“推到 GitHub 上”

$ git push

fetch：同事往 GitHub 推了新存档（紫色）。fetch 只是把它下载下来给你看看，不会动你正在改的文件。

对 AI 说“看看远程有什么更新，先别合并”

$ git fetch

pull：下载并合并进你的代码，相当于 fetch + merge。平时想“同步一下最新代码”，用它就行。

对 AI 说“拉一下最新的代码”

$ git pull

04 · 协作

参与别人的项目：Fork → 修改 → Pull Request

别人的仓库你没有修改权限，所以先复制一份到自己名下改，再“申请合并”。这个申请就叫 Pull Request（PR）。

Fork：在 GitHub 网页上点一下 Fork，把原项目完整复制一份到你的账号下。这份副本完全属于你。

对 AI 说“帮我 fork 这个仓库”

$ gh repo fork <原项目地址>

Clone：把你名下的副本下载到电脑上（上一页讲过）。

对 AI 说“把我 fork 的仓库 clone 下来”

$ git clone <你的副本地址>

新建分支，修改并提交：别直接改 main，开一个新分支（第 2 章学过），改完后 commit。

对 AI 说“新建分支 add-my-card，加上我的卡片后提交”

$ git switch -c add-my-card

Push：把这个分支上传到你的副本（origin）。原项目这时还看不到。

对 AI 说“推到我的 fork 上”

$ git push -u origin add-my-card

发起 Pull Request：请原项目的维护者把你的改动“拉”过去。PR 页面会列出你改了什么，大家可以在上面讨论。

对 AI 说“帮我提个 PR，标题和说明写清楚”

$ gh pr create

审查与合并：维护者看过、自动检查（CI）也通过后，点击合并。你的改动就正式进入原项目了。

对 AI 说“看看我的 PR 检查过了没有”

$ gh pr checks

保持同步：原项目会不断更新。下次开工前，先把原项目的最新改动同步到本地，再开新分支。

对 AI 说“先同步上游最新的 main，再开新分支”

$ git fetch upstream $ git merge upstream/main

04 · 协作 · 了解即可

合并 PR 时的 3 个按钮

假设你的 PR 里有 3 个存档：c1、c2、c3。维护者点不同的按钮，合进 main 之后的历史长得不一样。

Merge commit

保留全部 3 个存档，再加一个合并节点。记录最完整，但 PR 多了以后，历史线会越来越乱。

开源项目最常用

Squash and merge

把 3 个存档压成 1 个。一个 PR 对应一条记录，历史最干净。

Rebase and merge

把 3 个存档按顺序接到 main 的最后。每一笔都保留，历史还是一条直线。

作为贡献者，这一步你不用选，是维护者的事。知道有这 3 种方式，看到历史长得不一样时不会困惑，就够了。

04 · 协作

把 Git 交给 AI：你说清楚，它来敲命令

装好 git 和 GitHub 官方命令行工具 gh，运行一次 gh auth login 登录。之后提交、推送、提 PR、看检查结果，都可以直接开口。

你对 AI 说AI 实际会运行
“我改完了，帮我提交，推到一个新分支”git switch -c · git commit · git push
“给这个改动提个 PR，标题写清楚”gh pr create
“看看 PR 的自动检查过了没有”gh pr checks
“上游有更新吗？有冲突先告诉我，别直接覆盖”git fetch upstream · git merge
“刚才那次提交不要了，但改动先留着”git reset --soft HEAD~1
写进你的 AI 规则里：“执行 reset --hard、push --force、删除分支这类会丢东西的操作之前，先说明影响，等我确认。”
提 Issue 一定要自己过目：AI 很容易写出又长又空、甚至编造复现步骤的内容，白白浪费维护者的时间。可以让它起草，但要你核对后再发。
